# Kao ID R13A — สิทธิ์บริหารกลาง

ติดตั้งต่อจาก R12C โดยแตก ZIP ที่รากโปรเจกต์ ชุดนี้มีเฉพาะไฟล์เปลี่ยนแปลง ไม่ใช่โปรเจกต์เต็ม

## สิ่งที่แก้
- สิทธิ์เก่าและใหม่ใช้สถานะบัญชีและเซสชันจริง พร้อมวันเริ่ม/หมดสิทธิ์ ขอบเขตหมดอายุคือ expires_at > เวลาปัจจุบัน
- Owner ใช้ company_owners ของบัญชีเดิมเท่านั้น ไม่มีการแต่งตั้งหรือเปลี่ยน Owner จริงในชุดนี้ และไม่ใช้เจ้าขององค์กรเป็น Owner ระบบ
- ยกเลิกการอ้าง profile.role เพื่อให้สิทธิ์แอดมิน ใช้รายการแต่งตั้งที่ยังมีผลแทน
- KYC Officer ที่ยังไม่มี Kao ID ตามข้อยกเว้นเจ้าหน้าที่คนแรก ใช้เมนูและสิทธิ์ตรวจได้ตรงกัน ไม่ถือว่าผ่าน KYC และไม่ได้รับสิทธิ์ admin/super_admin
- บทบาทอื่นยังใช้เงื่อนไข KYC และ Kao ID เดิม สิทธิ์มอบหมาย/ถอนเจ้าหน้าที่และเปลี่ยน Owner สงวนให้ Owner แม้ตารางสิทธิ์เก่าเคยระบุ super_admin
- รายการสิทธิ์ก่อนแต่งตั้งไม่แสดงสิทธิ์สงวนดังกล่าว รายการแต่งตั้งคำนวณเงื่อนไข KYC ให้ตรงกับการใช้งานจริง
- หน้ารวมตรวจใหม่ตอนเข้า กลับจากหน้าลูก กลับเข้าแอป และเป็นระยะ หน้าจัดการสมาชิก/เจ้าหน้าที่/ตรวจเอกสารรีเฟรชเช่นกัน
- รายละเอียดและกล่องภาพหลักฐานซ่อนเมื่อผลตรวจสิทธิ์ไม่อนุญาตหรือโหลดสิทธิ์ไม่ได้ มีทางลองใหม่ ใช้ข้อความเดิมครบเจ็ดภาษา
- การตรวจเซสชันกลางรีเฟรช provider สิทธิ์เมนูที่กำลังถูกใช้งานด้วย จึงรับสิทธิ์ใหม่โดยไม่ต้องเปลี่ยนบัญชี
- คำสั่งแต่งตั้ง/ถอนจากแอปแนบ UUID ผู้เริ่มทำรายการ ป้องกันสลับบัญชีระหว่างทำรายการ
- ฟังก์ชันรายชื่อเจ้าหน้าที่เก่าไม่ตัดคนที่ยังไม่มี Kao ID และแก้ชนิดข้อมูลตอบกลับที่ไม่ตรง
- คงกฎห้ามตรวจ KYC ตนเอง และคงการปิด client RPC อนุมัติธุรกิจ/การเงินเก่าตาม R11A

เซิร์ฟเวอร์ตรวจสิทธิ์ทุกคำสั่ง ไม่รอให้เมนูรีเฟรช หน้าจอใช้รอบรีเฟรช 15–30 วินาทีและเมื่อกลับเข้าแอป ไม่ใช่การลบข้อมูลที่เคยดาวน์โหลดออกจากอุปกรณ์ผู้ใช้

## หลักฐานตรวจ
ฐานข้อมูลติดตั้งแล้ว ห้ามรัน migration ซ้ำเป็นขั้นตอนติดตั้ง ZIP ปกติ:
1. access.sql
2. staff_snapshot.sql
3. legacy_assignments.sql (รวมแก้ชนิดข้อมูลแล้ว)

SQL check_1, check_2a, check_2b, check_3 ผ่านด้วยข้อมูลชั่วคราวและ rollback:
- Owner, สมาชิก, เจ้าหน้าที่คนแรก, ไม่ยกระดับเป็นผู้ดูแลระบบทั่วไป
- UUID ผู้ทำรายการผิด, ผู้ไม่มีสิทธิ์เรียกคำสั่ง, ส่งซ้ำไม่เพิ่ม assignment/audit ซ้ำ
- หมดสิทธิ์พอดีเวลาปัจจุบัน, สิทธิ์ในอนาคต, บัญชีถูกระงับ
- JWT อ้างเซสชันที่ไม่มีในฐานข้อมูลถูกปฏิเสธ (จำลองสภาพหลังยุติเซสชัน)
- ถอนแล้วคำสั่งสิทธิ์ถัดไปไม่ผ่าน; ไม่เปิดช่องอนุมัติเก่ากลับมา
- รายชื่อเจ้าหน้าที่เก่ารองรับผู้ไม่มี Kao ID

## ทดสอบใช้งานจริงเพื่อปิดชุด
ใช้บัญชีทดสอบที่ไม่ใช่ Owner:
1. Owner แต่งตั้ง KYC Officer และตรวจว่าอีกบัญชีเห็นทางเข้าตรวจเอกสาร
2. เปิดรายละเอียดไว้ แล้ว Owner ถอนสิทธิ์ อีกบัญชีต้องทำคำสั่งใหม่ไม่ได้และหน้าจอซ่อนข้อมูลเมื่อรีเฟรช
3. เปิด URL ผู้ดูแลด้วยสมาชิกทั่วไป ต้องไม่โหลดข้อมูลผู้ดูแล
4. เจ้าหน้าที่เปิดหลักฐาน ตรวจคำขอของผู้อื่นได้ตามขั้นเดิม และอนุมัติของตนเองไม่ได้
5. ตรวจรายชื่อ/ประวัติหลังส่งซ้ำหรือกดลองใหม่ ต้องไม่เกิดรายการซ้ำ
6. Owner ยังเข้าได้ทั้งสมาชิก เจ้าหน้าที่ ตรวจเอกสาร และอนุญาตพาร์ตเนอร์

## ขอบเขตที่ยังต้องแยก
ชุดนี้ปิดจุดที่พบในสิทธิ์บริหารกลาง ไม่ใช่ใบรับรองความปลอดภัยทั้งเว็บ ยังต้องผลทดสอบแอปจริงและชุด Flutter ข้างต้น
Marketplace ดูแลสถานะคำสั่งซื้อ/ชำระเงิน/ขนส่งภายหลัง ชุดนี้ไม่เปิด API ผู้ให้บริการ ไม่รับหรือจ่ายเงินจริง
ระบบองค์กรเต็มวงจร, MFA/การกู้คืน Owner, SMS จริง, อีเมลเหตุการณ์, นโยบายข้อมูลและ load/security test ยังอยู่ในแผนก่อนเปิดสาธารณะ
Security Advisor ยังแจ้งฟังก์ชันธุรกิจเดิมที่ client เรียกได้, extension ใน public และ leaked-password protection ที่ยังปิด จึงไม่รายงานว่า advisor สะอาดทั้งหมด
- https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable
- https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable
- https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public
- https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
ตาราง private ที่ไม่มี policy เป็นการปิด client access โดยตั้งใจ ไม่เพิ่ม policy เพื่อให้คำเตือนหาย
