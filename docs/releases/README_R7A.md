# Kao ID R7A — บัตรประชาชน

ใช้ต่อจาก R6D ที่อ๊อฟรันผ่าน 107 tests แล้ว (26 กันยายน 2026)

## สิ่งที่เปลี่ยน
- เปลี่ยนหน้าบัตรประชาชนจากการเลือกไฟล์ในเครื่อง เป็นแบบฟอร์มชื่อ เลขบัตร วันที่ออก/หมดอายุหรือตลอดชีพ รูปหน้าและหลัง
- ตรวจ JPEG/PNG ขนาด 10 MB รูปด้านละอย่างน้อย 100 พิกเซล ไม่เกิน 24 ล้านพิกเซล และไม่รับภาพเคลื่อนไหว; แปลงรูปเป็น JPEG ก่อนส่ง
- อัปโหลดไป private bucket `identity-documents` ที่มีอยู่จริง
- บันทึกเอกสาร รูปสองด้าน และคำขอรอตรวจสอบในธุรกรรมฐานข้อมูลเดียวกัน
- ตรวจเจ้าของจาก session ฝั่ง server; ไม่มีพารามิเตอร์ให้ผู้ใช้ตั้งผู้อนุมัติหรืออนุมัติตนเอง
- ส่งซ้ำในหน้าที่ยังเปิดอยู่ใช้ document ID เดิม; หลังผลตอบกลับขาดหายสามารถตรวจสอบผลหรือส่งซ้ำได้
- เปิดกลับมาอ่านสถานะล่าสุดและดูรูปผ่านสิทธิ์เจ้าของ ไม่สร้าง public URL
- ข้อความใหม่ครบไทย–อังกฤษ รวมข้อความผิดพลาด ปุ่ม และวันที่ตาม locale
- เพิ่ม pending_review ในตัวแสดงสถานะเดิม; คงขั้นตอนอีเมลและโทรศัพท์เดิม

## สถานะฐานข้อมูล
ติดตั้ง migration `national_id_atomic_submission_r7a` ในโปรเจกต์เดิมแล้ว ไม่ต้องนำ SQL ไปรันซ้ำ
`docs/R7A_backend.sql` เป็นสำเนาสำหรับตรวจสอบและย้ายสภาพแวดล้อม
ไม่ได้แก้สถานะเอกสารจริงของผู้ใช้ และไม่ได้สร้าง Kao ID จากการส่งเอกสาร

ทดสอบบนฐานข้อมูลแล้ว (transaction rollback):
- เอกสารหนึ่งรายการ มีรูป 2 รายการและคำขอ pending หนึ่งรายการ
- ส่งซ้ำ document ID เดิมไม่เพิ่มคำขอ
- ปฏิเสธ path ที่ไม่ใช่เจ้าของ/รายการนั้น
- บัญชีอื่นอ่านเอกสารและ metadata รูปไม่ได้ผ่าน RLS
- anon ไม่มีสิทธิ์เรียก RPC; bucket ยังคง private
- ไม่เหลือรายการทดสอบในฐานข้อมูล

เป็นการทดสอบ SQL ด้วย metadata จำลอง ไม่ใช่การทดสอบส่งรูปผ่าน Chrome

## ทดลองใช้งานจริง
1. เปิดหน้ายืนยันตัวตน → บัตรประชาชน แล้วลองไทยและอังกฤษ
2. ใช้บัญชีทดสอบและรูปตัวอย่างที่ไม่ใช่เอกสารส่วนตัวจริงในรอบทดสอบแรก
3. กรอกชื่อ เลขบัตร 13 หลัก วันที่ และเลือกรูปหน้า/หลัง; รูปต้องแสดงก่อนส่ง
4. ส่งแล้วต้องเป็น “รอตรวจสอบ” ไม่ใช่ “ยืนยันแล้ว”
5. กลับหน้ารวมแล้วเปิดใหม่ ต้องพบสถานะและดูรูปทั้งสองด้านได้
6. รีเฟรช/ส่งซ้ำหลังเน็ตขาด ต้องไม่มีคำขอซ้ำ; ล็อกอินบัญชีอื่นต้องไม่เห็นรูปนั้น
7. หากติดปัญหา ส่งข้อความ error จาก console โดยไม่ส่งรูปบัตร เลขบัตร หรือ token

## ข้อจำกัดที่ต้องทราบก่อนเปิดจริง
- ตรวจเลขบัตรเพียงรูปแบบ 13 หลัก ยังไม่ตรวจเลข checksum หรือยืนยันกับฐานข้อมูลภาครัฐ
- ตรวจ bytes รูปใน client; server ตรวจเจ้าของ path, ขนาด และ MIME metadata เท่านั้น ยังไม่มี server-side image scanning
- Storage upload และธุรกรรม Postgres เป็นคนละขั้นตอน หากปิดหน้าระหว่างส่งอาจมีไฟล์กำพร้า ต้องเพิ่มระบบเก็บกวาดตามอายุ; ไม่ลบทันทีเมื่อผล RPC ไม่แน่นอน
- รายการเดิมที่ไม่มี metadata รูป หรือใช้ path เก่า อาจเปิดรูปไม่ได้ ต้องตรวจย้ายข้อมูลแยก ไม่แก้/ลบทับเอกสารเดิม
- การพิจารณาอนุมัติ/ปฏิเสธและออก Kao ID ยังต้องตรวจระบบเจ้าหน้าที่ครบวงจร
- รูปหลังบัตรเป็นข้อมูลอ่อนไหว ต้องกำหนดวัตถุประสงค์ ระยะเก็บ และสิทธิ์เจ้าหน้าที่ก่อน production
- นี่คือชุดพัฒนาหน้าบัตรประชาชน ไม่ใช่การรับรองว่า Kao ID ทั้งระบบพร้อม production

## ลำดับงานต่อ
1. ยืนยันผล analyzer/tests และส่งรูปจริงจาก Chrome ของชุดนี้
2. ทำหนังสือเดินทางให้บันทึก/เปิดรูปจริงครบ โดยใช้แนวทางตรวจเจ้าของและสถานะเดียวกัน
3. ใบพำนักและบัญชีธนาคาร: เชื่อมงานที่ยังเป็นปุ่มเตรียมไว้ และทดสอบไทย/อังกฤษ
4. โทรศัพท์: ทดสอบ OTP กับผู้ให้บริการที่ตั้งค่าได้; อีเมลคงผลที่ผู้ใช้เคยยืนยันผ่านไว้
5. ปรับสถานะ contact ในหน้ารวมให้ตรงกับหลักฐานการยืนยันจริง (ไม่ถือ auto-confirm ตอนสมัครเป็นหลักฐาน ownership)
6. เจ้าหน้าที่ตรวจ KYC → ออก Kao ID → สิทธิ์ใช้ Marketplace; audit security ก่อนเปิดจริง

Security advisor พบรายการเดิมที่ต้องตรวจต่อ: ฟังก์ชัน SECURITY DEFINER ที่เปิดให้ anon/authenticated, trigger search_path, บางตารางมี RLS แต่ไม่มี policy, leaked password protection
ชุด R7A ไม่ได้ขยายสิทธิ์เขียนตาราง identity_documents ให้ client และ RPC ใหม่ไม่ปรากฏในรายการเตือนนั้น
